## ขอบเขตที่ตรวจด้วยโค้ด

ระบบครอบคลุม parsing คำสั่งธุรกรรม/รายงาน/เสียง, รายงานการเงินจริงตามเขตเวลาไทย, structured output ของ AI, fallback ของ AI categorization, transaction soft-delete/audit, และ scheduler regressions. การถอดเสียงจาก LINE และ AI analysis ต้องทดสอบกับ event จริงหลัง deployment เนื่องจากเกี่ยวข้องกับ LINE media API และบริการภายนอก

## การยืนยันจาก LINE จริง

หลังเผยแพร่รุ่น `edfb69e6` ผู้ใช้ยืนยันว่าไมโลถอดข้อความเสียงจาก LINE ได้สำเร็จแล้ว การแก้ไขใช้ signed S3 URL สำหรับให้บริการถอดเสียงเข้าถึงไฟล์ได้ โดย workflow ยังคงเสนอข้อความก่อน และจะไม่สร้างธุรกรรมจนกว่าผู้ใช้จะพิมพ์ `ยืนยันเสียง`.

หลังเผยแพร่รุ่น `9b06f9fb` ผู้ใช้ยืนยันว่าเลือกยืนยันจากข้อเสนอเสียงแล้ว ไมโลบันทึกรายจ่าย **80 บาท** ในหมวด **อาหาร** สำเร็จ จึงยืนยันทั้งการส่ง action จาก UI ของ LINE และการสร้างธุรกรรมแบบ explicit confirmation.

หลังเผยแพร่รุ่น `94e54d21` ผู้ใช้ยืนยันว่าการตอบกลับจากเสียงสามารถนำไปสู่การบันทึกรายจ่าย **55 บาท** ในหมวด **อาหาร** ได้สำเร็จ ยืนยันว่า voice proposal workflow และ explicit confirmation ยังคงทำงานหลังปรับรูปแบบการ์ดใหม่.

## Automated regression: post-save summary and voice category editing

เพิ่ม regression test สำหรับการ์ดหลังบันทึกรายการ โดยตรวจว่า Flex payload แสดงยอดธุรกรรมและยอดรายวันที่ส่งผ่านมาจากรายงานจริง พร้อม action `สรุปวันนี้` และตรวจข้อความน้องแมวแบบ deterministic ที่ช่วงยอดไม่เกิน 100 บาท, 101–500 บาท และมากกว่า 500 บาท

เพิ่ม regression test สำหรับ flow `แก้ไขข้อความเสียง` ให้ตอบ Quick Reply หมวดยอดนิยม และให้ action `เปลี่ยนหมวดเสียง <หมวด>` อัปเดตเฉพาะข้อเสนอที่ยังเป็น `proposed` ก่อนส่ง Flex proposal ใหม่ โดยไม่มีการสร้างธุรกรรมจนกว่าผู้ใช้จะยืนยันอย่างชัดแจ้ง นอกจากนี้ได้ครอบคลุมการยืนยันรายการจากใบเสร็จ/สลิปให้ส่งการ์ดสรุปยอดหลังสร้างรายการแล้ว

## Visual refinement: Milo post-save card

ปรับ Flex card หลังบันทึกให้ใช้ hierarchy แบบการ์ดยืนยันชัดเจน ได้แก่ แถบสถานะสำเร็จ, แผงรายละเอียดธุรกรรม, สรุปยอดรายวันแยกรายรับ/รายจ่าย และยอดคงเหลือ โดยเปลี่ยนชุดสีเป็นม่วงอ่อน `#F2F0FF`, มิ้นท์ `#E4F8F2` และชมพู `#FDECF2` ตามธีมของไมโล ไม่คัดลอกการแสดงงบประมาณหรือช่องทางชำระเงินจากภาพอ้างอิง เพราะข้อมูลดังกล่าวไม่ได้มีอยู่ในธุรกรรมที่ยืนยันแล้วและจะขัดกับหลักการไม่สร้างข้อมูลจำลอง

การตรวจอัตโนมัติยืนยันสีพื้นหลัง โครงสร้างแผงย่อย เครื่องหมายยืนยัน ยอดธุรกรรม ยอดสรุปรายวัน และ action `สรุปวันนี้`; คำสั่ง `pnpm exec tsc --noEmit`, `pnpm test -- --run` รวม 73 กรณี และ `pnpm build` ผ่านทั้งหมด

## Bug fix: LINE rejects post-save Flex payload

production log ของวันที่ 27 ส.ค. 2569 ระบุว่า LINE ปฏิเสธการ์ดที่ path `/body/contents/0/contents/0/cornerRadius` ด้วย HTTP 400 หลังธุรกรรมถูกบันทึกแล้ว จึงไม่สามารถใช้ reply token เดิมส่งข้อความสำรองได้ในบางครั้ง แก้ payload โดยเปลี่ยนค่ามุมขององค์ประกอบสถานะเป็นค่ามาตรฐาน `md` และเพิ่มลำดับสำรองเป็น Flex → text Quick Reply → push ข้อความสรุป หาก reply token ไม่สามารถใช้ซ้ำได้ ทั้งสามข้อความใช้ข้อมูลสรุปรายวันชุดเดียวกัน

เพิ่ม regression สำหรับกรณีที่ Flex และ text fallback ถูกปฏิเสธพร้อมกัน โดยยืนยันว่าไมโลส่ง push ข้อความสรุปแทนได้โดยไม่สร้างธุรกรรมเพิ่ม การตรวจ `pnpm exec tsc --noEmit`, `pnpm test -- --run` รวม 74 กรณี และ `pnpm build` ผ่านทั้งหมด การยืนยัน payload จาก LINE จริงจะทำหลังเผยแพร่ โดยผู้ใช้เป็นผู้เลือกว่าจะส่งรายการธุรกรรมจริงหรือไม่

## LINE daily financial summary card

ปรับคำสั่ง `สรุปวันนี้` และ `สรุปการเงินวันนี้` ให้ตอบด้วย Flex card ใน hierarchy และชุดสีเดียวกับการ์ดหลังบันทึกรายจ่าย โดยมีหัวข้อสรุป, กล่องรายรับและรายจ่าย, ยอดกำไร/คงเหลือ และรายจ่ายตามหมวดที่เรียงจากข้อมูลจริงเท่านั้น หาก Flex ถูกปฏิเสธ ระบบจะตอบข้อความสรุปเดิมก่อน และจะ push ข้อความหาก reply token ใช้ไม่ได้

เพิ่ม regression test สำหรับ parser alias, LINE payload และ webhook command ที่มีรายรับ 0 บาท รายจ่าย 615 บาท คงเหลือ -615 บาท หมวดอาหาร 565 บาท และทั่วไป 50 บาท ซึ่งเป็นข้อมูลทดสอบใน unit test เท่านั้น การตรวจ `pnpm exec tsc --noEmit`, `pnpm test -- --run` รวม 76 กรณี และ `pnpm build` ผ่านทั้งหมด

### Validation with LINE Messaging API

ทดสอบ payload ของ Flex report card กับ endpoint `POST /v2/bot/message/validate/reply` ของ LINE โดยไม่ส่งข้อความถึงผู้ใช้ และได้รับ HTTP 200 พร้อม `{}` จึงยืนยันว่า schema ของ message object ถูกต้องตาม API ณ เวลาทดสอบ ทั้งนี้ endpoint มีไว้ตรวจ message objects และไม่ยืนยันการแสดงผลบนอุปกรณ์ผู้รับ จึงยังต้องเก็บผลทดสอบจาก LINE จริงต่อไป [1]

[1]: https://developers.line.biz/en/reference/messaging-api/#validate-reply-message-objects "LINE Messaging API reference — Validate message objects"

### Investigation after production deployment

ตรวจ webhook ล่าสุดของคำสั่ง `สรุปการเงินวันนี้` พบว่า event ถูกบันทึกเป็น `processed` โดยไม่มี error และคำสั่งมีช่องว่างท้ายข้อความ ซึ่ง parser ตัดช่องว่างก่อนจับ intent อยู่แล้ว จึงเพิ่ม telemetry ที่บันทึกเฉพาะ endpoint และ HTTP status หลัง LINE รับข้อความสำเร็จ โดยไม่บันทึก reply token หรือเนื้อหาแชท การตรวจ TypeScript, Vitest 76 กรณี และ production build ผ่าน ก่อนขอผลทดสอบจริงหลังเผยแพร่

หลังเผยแพร่ ผู้ใช้ส่ง `สรุปการเงินวันนี้` อีกครั้งและยืนยันว่าได้รับ Flex card แล้ว ขณะที่ production telemetry บันทึก `POST /v2/bot/message/reply` เป็น HTTP 200 จึงปิดผลการทดสอบจริงของการ์ดรายงานประจำวันได้ โดยไม่มีการสร้างหรือแก้ไขธุรกรรมระหว่างการตรวจครั้งนี้

## Milo finance branding and period cards

เพิ่มแถบกราฟิกแบรนด์ `MILO • FINANCE` พร้อมภาพน้องแมวและสัญลักษณ์สีมิ้นท์ใน Flex card สรุปการเงิน โดยใช้พาสเทลม่วง `#F2F0FF`, ชมพู `#FCEAF4` และมิ้นท์ `#5AC6AD` และไม่แสดงตัวเลขที่ไม่ได้มาจากรายงานจริง

การ์ดมีปุ่มเรียกดู `สรุปวันนี้`, `สรุปสัปดาห์นี้` และ `สรุปเดือนนี้`; webhook test ยืนยันว่าแต่ละคำสั่งอ่านรายงานตามช่วงเวลาที่ถูกต้อง และ LINE validation endpoint ตอบ HTTP 200 สำหรับ payload ทั้งรายวัน รายสัปดาห์ และรายเดือน โดยไม่มีการส่งข้อความถึงผู้ใช้ระหว่างตรวจ ผู้ใช้เลือกให้ไมโลส่งรายงานเฉพาะเมื่อกดดูหรือพิมพ์คำสั่ง จึงไม่มีการเปิดงานส่งรายวันอัตโนมัติ

หลังเผยแพร่ ผู้ใช้ทดสอบ `สรุปสัปดาห์นี้` และ `สรุปเดือนนี้` ใน LINE และยืนยันว่าได้รับการ์ดครบทั้งสองคำสั่ง จึงยืนยันการทำงานจริงของปุ่มและคำสั่งสรุปหลายช่วงเวลาได้ โดยไม่มีการสร้างหรือแก้ไขธุรกรรมเพิ่มเติม

## Finance digest schedule and category expansion

ตามการยืนยันของผู้ใช้ ไมโลจะส่งรายงานอัตโนมัติไปยัง LINE ส่วนตัวที่เชื่อมไว้เวลา 06:00 น. ตามเวลาไทยทุกวัน และ 06:00 น. ทุกวันจันทร์ โดยรายงานรายวันครอบคลุม **วันก่อนหน้า** และรายงานประจำสัปดาห์ครอบคลุม **จันทร์–อาทิตย์ที่ปิดรอบแล้ว** เพื่อไม่ส่งการ์ดที่มีเพียงรายการช่วงเช้าของวันใหม่

เพิ่มตาราง `finance_digest_deliveries` ที่มี unique key ตาม setting และ period เพื่อกันการส่งซ้ำ พร้อมสถานะ `sending`, `sent` และ `failed` และ audit event ที่ไม่บันทึกยอดหรือข้อความรายละเอียด รายการ standard categories รองรับทั้งรายจ่าย เช่น ที่อยู่อาศัย ค่าสาธารณูปโภค ประกัน และหนี้สิน และรายรับ เช่น เงินเดือน งานอิสระ ขายสินค้า/บริการ ดอกเบี้ย/เงินปันผล และเงินคืน โดยยังคงหมวดรายจ่ายแบบกำหนดเองเดิมไว้

การตรวจ TypeScript, Vitest รวม 80 กรณี และ production build ผ่านแล้ว รวมถึง test ของ Bangkok window, การกันส่งซ้ำ, Flex-to-text fallback, payload push card และการจำแนกหมวดจากข้อความภาษาไทย

หลังเพิ่มกราฟิกธีมไมโล ผู้ใช้เรียก `สรุปสัปดาห์นี้` ใน LINE และ production telemetry ยืนยัน `POST /v2/bot/message/reply` เป็น HTTP 200 จากนั้นผู้ใช้ยืนยันว่าเห็นการ์ดแล้ว งานส่งอัตโนมัติถูกลงทะเบียนเป็นสรุปวันก่อนหน้าทุกวันเวลา 06:00 น. และสรุปสัปดาห์ก่อนหน้าทุกวันจันทร์เวลา 06:00 น. ตาม Asia/Bangkok โดยตรวจสถานะ enabled และ callback path แล้ว

การทดสอบเรียกใช้ผ่าน LINE แบบผู้ใช้พิมพ์คำสั่งยืนยันการ์ดสรุปรายสัปดาห์สำเร็จแล้ว อย่างไรก็ตาม การเร่งรอบ cron ชั่วคราวจาก sandbox พบ timeout ที่ผู้ให้บริการตารางเวลา และไม่มี execution record จึงไม่ถือเป็นผลยืนยันการส่งแบบอัตโนมัติ ระบบได้กู้คืน job รายวันด้วย task ใหม่ที่ใช้ cron `0 0 23 * * *` UTC และ job รายสัปดาห์ใช้ cron `0 0 23 * * 0` UTC ซึ่งเท่ากับ 06:00 น. Asia/Bangkok ทุกวัน และ 06:00 น. วันจันทร์ตามลำดับ พร้อมตรวจว่า task ทั้งสอง enabled และถูกอ้างอิงจาก `automation_settings` แล้ว รอบอัตโนมัติแรกจะเป็นหลักฐาน delivery audit ที่ต้องตรวจหลังเวลาทำงานจริง
